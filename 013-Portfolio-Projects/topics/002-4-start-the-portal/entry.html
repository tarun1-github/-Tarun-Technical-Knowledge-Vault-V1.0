Problem Area – Why We Created the Access Verification Tool

1 Access SPOC managing access for ~40 engineers, making manual tracking difficult.

Engineers rarely checked their access proactively, resulting in access getting revoked.

Access revocation created avoidable operational impact and delays.

Client had to provide approvals repeatedly whenever access needed to be restored.

No structured mechanism was available for the Access SPOC to monitor access status.

SPOC could only act reactively after receiving an access-related notification.

Individual follow-ups with 40 engineers were time-consuming and difficult to manage.

When access was revoked, engineers had to:

Raise an ARM request with the bank/client.

Wait for client approval.

Follow up until access was restored.

The overall process was manual, reactive, and dependent on multiple stakeholders.

The tool was created to enable a proactive, centralized, and structured access verification process.

Goal: identify access issues early, reduce manual follow-ups, avoid unnecessary access revocation, and minimize client dependency.

LF will be replaced by CRLF the next time Git touches it why we get this

Yes, this is a normal Git warning on Windows, not an error.

What does LF → CRLF mean?

Text files have different ways of representing a new line:

"This file currently uses LF. The next time Git/Windows rewrites it, I'll convert it to CRLF."

Linux / macOS:

LF = \n

Windows:

CRLF = \r\n

Your project is being edited on Windows, while some files were created/maintained with Linux-style LF endings.

Add a .gitattributes file at the root of your project:

* text=auto eol=lf

Then configure Git:

git config --global core.autocrlf false

This tells Git:

Don't automatically convert LF ↔ CRLF
