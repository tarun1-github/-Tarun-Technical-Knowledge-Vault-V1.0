Embedding
OpenAI's text-embedding-3-large takes text as input and converts it into a list of numbers.

"How do I troubleshoot a Cisco phone?"
                 ↓
       text-embedding-3-large
                 ↓
[0.021, -0.034, 0.087, 0.112, ...]

======================================

That list of numbers is called an embedding/vector.

OpenAI's text-embedding-3-large can produce embeddings with up to 3072 dimensions.

A vector of 3072 dimensions means that one piece of text is represented as a list of 3,072 numerical values

3072 dimensions ≠ 3072 words or 3072 pieces of information.
It simply means the numerical representation has 3,072 coordinates.That's a 2-dimensional vector.

Text → [3072 numbers]

##Your vector database needs to create a field that expects:

Vector field
├── Dimension 1
├── Dimension 2
├── Dimension 3
├── ...
└── Dimension 3072

##If you're using an embedding model that produces 3072 dimensions:
Embedding Model
      │
      │ "Cisco phone registration issue"
      ▼
[0.021, -0.034, 0.087, ... 0.015]
      │
      │ 3072 numbers
      ▼
Vector Database
      │
      └── vector field: dimension = 3072
	  
###Then when you perform a search:
User question
     ↓
Embedding model
     ↓
3072-dimensional vector
     ↓
Vector DB
     ↓
Compare against stored 3072-dimensional vectors
     ↓
Similarity score

###Vector Embedding and vector store  DB (Chroma)

The rule to remember

Embedding model dimension = Vector database field dimension

❌ What happens if dimensions don't match?

Suppose your database is configured: dimension = 1536

but your embedding model produces: dimension = 3072

You can't directly store/search that vector.

You'd effectively be trying to put: [3072 values]

into a container designed for: [1536 values]

The vector database will normally return a dimension mismatch/error.

FAISS : Facebook AI similarity search its library for similarity search

## similarity search
Given a user's question, find the stored chunks whose meaning is most similar to the question.

Similarity search is the process of comparing a query embedding with stored document embeddings and retrieving the most semantically similar chunks.

User asks:

❓ "My Cisco phone is not registering. How can I fix it?"

The system first converts the question into an embedding:

Question
   ↓
Embedding Model
   ↓
[0.12, -0.04, 0.87, ... 3072 values]

Then it compares this vector against the vectors stored in the Vector DB.

========================================
One-line memory trick

Embedding = convert text → numbers

Similarity Search = compare numbers → find closest meaning
Cosine similarity tells us how similar two vectors are by measuring the angle between them.

Cosine Similarity
                A · B
Cos(A,B) = ─────────────
             ‖A‖ × ‖B‖

If the angle θ is small, the vectors point in almost the same direction → high similarity.
If the angle is large → low similarity.

RAG = retrieve those closest chunks → give them to the LLM → generate answer.

But embeddings capture semantic meaning, so similarity search can recognize:

"phone isn't connecting"
          ≈
"endpoint registration failure"

That's why embeddings are powerful in RAG.

Structured Output

Structured output means asking the LLM to return its answer in a predefined format/schema instead of normal free-form text.This is useful when the LLM's response needs to be parsed, stored, or passed to another program/tool.

### Pydantic
Pydantic models provide the richest feature set with field validation, descriptions, and nested structures.
because of field validation , value of string should string only else encounter with error.

One common LangChain approach is a Pydantic schema:

from pydantic import BaseModel, Field


class Person(BaseModel):
    name: str = Field(description="Person's name")
    age: int = Field(description="Person's age")
    profession: str = Field(description="Person's profession")
	
Then provide this schema to the model:

structured_model = model.with_structured_output(Person)

result = structured_model.invoke(
    "Tarun is 43 years old and works as a Python developer."
)

print(result)

TypedDict is a Python typing feature that lets you define the expected structure of dictionary data.
In LangChain, it can be used as a schema for structured output when you want to describe the expected fields but don't need runtime validation like Pydantic provides.

--------No runtime validation of fields/data types.

Remember: TypedDict describes the shape of the data, while Pydantic can additionally validate the data at runtime.

 from typing import TypedDict
import random

from langgraph.graph import StateGraph, START, END


# ============================================================
# 1. Define the State
# ============================================================

class State(TypedDict):
    play: str


# ============================================================
# 2. Define the Nodes
# ============================================================

def start_play(state: State):
    print("Starting the game...")
    return state


def cricket(state: State):
    print("Playing Cricket 🏏")
    return {"play": "cricket"}


def badminton(state: State):
    print("Playing Badminton 🏸")
    return {"play": "badminton"}


# ============================================================
# 3. Define the Conditional Decision Function
# ============================================================

def random_play(state: State):
    """
    Randomly decide whether to play cricket or badminton.
    The returned string must match the destination node name.
    """

    play = random.choice(["cricket", "badminton"])

    print(f"Selected game: {play}")

    return play


# ============================================================
# 4. Build the Graph
# ============================================================

graph = StateGraph(State)


# Add nodes
graph.add_node("start_play", start_play)
graph.add_node("cricket", cricket)
graph.add_node("badminton", badminton)


# ============================================================
# 5. Define the Flow
# ============================================================

# START → start_play
graph.add_edge(START, "start_play")


# start_play → random decision → cricket OR badminton
graph.add_conditional_edges(
    "start_play",
    random_play
)


# cricket → END
graph.add_edge("cricket", END)


# badminton → END
graph.add_edge("badminton", END)


# ============================================================
# 6. Compile the Graph
# ============================================================

graph_builder = graph.compile()


# ============================================================
# 7. Execute the Graph
# ============================================================

initial_state = {
    "play": ""
}

result = graph_builder.invoke(initial_state)


# ============================================================
# 8. Print Final State
# ============================================================

print("\nFinal State:")
print(result)

What information should be given to each worker?

Problem 1 — Packages re-download every build

Consider dockerfile

FROM python:3.12
RUN pip install -r requirements.txt
COPY . .
If dependencies are downloaded during a build, rebuilding can cause unnecessary downloads.

Build 1
   ↓
Download Flask
Download LangChain
Download LangGraph
Download FastAPI
   ↓
Build

Build 2
   ↓
Download again ❌
This makes builds slower and wastes bandwidth.

Modern solution — Cache mounts
BuildKit allows a persistent cache to be mounted during the build.

Build 1
   ↓
Download packages
   ↓
Cache

Build 2
   ↓
Reuse cache ✅
   ↓
Only download what's missing

Consider dockerfile

##############################################################################

##############################################################################

# syntax=docker/dockerfile:1

FROM python:3.12

RUN --mount=type=cache,target=/root/.cache/pip \
pip install -r requirements.txt

The important concept:
Cache Mount
     ↓
Persist package cache between builds
     ↓
Faster rebuilds

Problem 2 — Secrets can leak

Suppose you need an API key during the build.
A bad approach is: The problem is that secrets can become part of the image's build history or metadata.

dockerfile
ARG API_KEY=[REDACTED]
RUN some-command --api-key=[REDACTED]

You can inspect image history with:  🚨 Never put production secrets directly into a Dockerfile.
docker history --no-trunc myapp

Modern solution — BuildKit secret mounts
dockerfile
# syntax=docker/dockerfile:1

FROM ubuntu
RUN --mount=type=secret,id=mysecret \
    cat /run/secrets/mysecret

Build:
docker buildx build --secret id=mysecret,src=mysecret.txt -t myapp .

Secret
   │
   ↓
BuildKit
   │
   ├── temporarily mounted
   │
   ↓
RUN command
   │
   ↓
Secret removed

Secret → available during build
Secret → NOT baked into final image
"BuildKit makes secrets impossible to leak."
'BuildKit makes secrets impossible to leak.'
BuildKit secret mounts prevent the secret from being persisted as part of the image layer when used correctly.

Problem 3 — Architecture lock-in
Traditional builds can result in an image built for a specific CPU architecture.

Developer machine
      ↓
x86/amd64
      ↓
Docker image
      ↓
Works on amd64

Then someone tries to run it on:ARM64  and you can encounter: exec format error
This becomes particularly important with:
Intel/AMD servers → amd64
Apple Silicon     → arm64
AWS Graviton      → arm64

Modern solution — Multi-platform builds
BuildKit/buildx can build for multiple architectures.

docker buildx build --platform linux/amd64,linux/arm64 -t myapp:latest .
You can use the same image name/tag: myapp:latest. This is called a multi-platform image.

                 myapp:latest
                      │
             ┌────────┴────────┐
             ↓                 ↓
        linux/amd64       linux/arm64
             │                 │
        Intel/AMD          ARM systems

Docker — CMD, ARG, ENTRYPOINT & Environment Variables

1. First understand: Why does a container exit?
This is the most important Docker concept.
	A container stays alive only while its main process is running.

docker run ubuntu ##Ubuntu starts, but there is no long-running foreground process.

Container   ##Docker doesn't keep the container alive just because you created it.
   ↓
Main process
   ↓
Process finishes
   ↓
Container exits

2. CMD — What should the container do by default?
CMD defines the default command that Docker should execute when the container starts.

dockerfile
FROM ubuntu
CMD ["sleep", "5"]

docker build -t ubuntu-sleeper .
docker run ubuntu-sleeper

After 5 seconds:
sleep finishes
      ↓
container exits

3. Override CMD

dockerfile
FROM ubuntu
CMD ["sleep", "5"]

docker run ubuntu-sleeper
But you can override the CMD: docker run ubuntu-sleeper sleep 10

Dockerfile CMD :: The Dockerfile hasn't changed.
sleep 5
   ↓
OVERRIDDEN
   ↓
sleep 10

4. ENTRYPOINT — The main program
'This container is designed to run this particular program.'
ENTRYPOINT = sleep
argument     = 10

5. ENTRYPOINT + CMD   ##This is where it becomes really useful.

dockerfile
FROM ubuntu
ENTRYPOINT ["sleep"]
CMD ["5"]

6. Override CMD while keeping ENTRYPOINT  ##docker run ubuntu-sleeper 10
ENTRYPOINT = sleep       ← stays
CMD = 5                  ← replaced with 10

7. ARG — Build-time variable
A variable available while building the image.

dockerfile
FROM ubuntu
ARG APP_VERSION=1.0
RUN echo "Building version $APP_VERSION"

docker build --build-arg APP_VERSION=2.0 -t myapp .

ARG → BUILD TIME
ENV → RUNTIME

docker run -e COLOR=blue myapp ##Docker passes: COLOR=blue

Different configuration.This (enviornment) is much better than rebuilding your application every time you want to change configuration.

Q1. Why does a Docker container exit?
A container remains running as long as its main/foreground process is running. When that process exits, the container stops.

Q2. What is CMD?
CMD defines the default command or arguments executed when a container starts.

Q3. What is ENTRYPOINT?
ENTRYPOINT defines the main executable that the container is designed to run.

Q4. What is ARG?
ARG is primarily a build-time variable used during Docker image construction.

Q5. Why use ENV?
Environment variables allow application configuration to be changed without modifying or rebuilding the application code/image.

Q6. What does docker inspect do?
It displays detailed low-level configuration and runtime information about Docker objects such as containers and images.

Problem Area – Why We Created the Access Verification Tool


1 Access SPOC managing access for ~40 engineers, making manual tracking difficult.
Engineers rarely checked their access proactively, resulting in access getting revoked.

Access revocation created avoidable operational impact and delays.
Client had to provide approvals repeatedly whenever access needed to be restored.
No structured mechanism was available for the Access SPOC to monitor access status.
SPOC could only act reactively after receiving an access-related notification.

Individual follow-ups with 40 engineers were time-consuming and difficult to manage.

When access was revoked, engineers had to:
Raise an ARM request with the bank/client.
Wait for client approval.
Follow up until access was restored.
The overall process was manual, reactive, and dependent on multiple stakeholders.
The tool was created to enable a proactive, centralized, and structured access verification process.
Goal: identify access issues early, reduce manual follow-ups, avoid unnecessary access revocation, and minimize client dependency.

LF will be replaced by CRLF the next time Git touches it  why we get this
	Yes, this is a normal Git warning on Windows, not an error.
	
	What does LF → CRLF mean?
Text files have different ways of representing a new line:
"This file currently uses LF. The next time Git/Windows rewrites it, I'll convert it to CRLF."

Linux / macOS:
LF  = \n

Windows:
CRLF = \r\n

Your project is being edited on Windows, while some files were created/maintained with Linux-style LF endings.

Add a .gitattributes file at the root of your project:

* text=auto eol=lf

Then configure Git:
git config --global core.autocrlf false
This tells Git:

Don't automatically convert LF ↔ CRLF
